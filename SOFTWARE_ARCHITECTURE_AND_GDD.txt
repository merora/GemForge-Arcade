GemForge Arcade คือเกมขนาดเล็กที่ทำงานบนบล็อกเชน หน้าตาเป็นตู้เกมนีออน
มีกติกาหลักดังนี้

  1. ผู้เล่นใช้เหรียญ "GEM" หยอดตู้กาชาเพื่อสุ่มรับไอเทม
  2. ไอเทมทุกชิ้นเป็น NFT คือมีเลขประจำตัวไม่ซ้ำกัน และมีเจ้าของชัดเจนบนบล็อกเชน
  3. นำไอเทมระดับเดียวกัน 2 ชิ้นมา "ผสม" (FORGE) เพื่อลุ้นได้ชิ้นที่หายากขึ้น
     ไอเทมที่ใช้ผสมจะถูก "เผาทิ้ง" ถาวร แล้วสร้างไอเทมชิ้นใหม่ขึ้นมาแทน
  4. นำสัตว์เลี้ยงมา "สวมเกราะ/ถือดาบ" (EVOLVE) เพื่อกลายร่างเป็นสัตว์พิเศษที่
     ไม่มีขายในตู้ (Craft-Only) และอัปเกรดได้จนถึงระดับสูงสุด "Mythic"
  5. นำไอเทมไปวางขายในร้านค้า (SHOP) ให้ผู้เล่นคนอื่นซื้อด้วยเหรียญ GEM
     โดยร้านหักค่าธรรมเนียม 5% แล้วเผาทิ้ง

ระดับสูงสุดของไอเทมทั่วไปคือ Legendary ซึ่งได้จากการผสมเท่านั้น ตู้กาชาไม่ปล่อยออกมา

ทุกอย่างรันบน "บล็อกเชนจำลองในเครื่อง" (Hardhat) จึงไม่ต้องใช้ MetaMask
ไม่ต้องใช้อินเทอร์เน็ตเพื่อทำธุรกรรม และไม่มีเงินจริงเกี่ยวข้อง

ส่วนประกอบหลัก
  - Smart Contract 4 ตัว (เขียนด้วยภาษา Solidity)
      GemToken     = เหรียญ GEM
      ItemNFT      = ไอเทม NFT
      GachaGame    = กติกาเกมทั้งหมด (สุ่ม / ผสม / สวมใส่)
      Marketplace  = ร้านค้า
  - หน้าเว็บ 1 หน้า (React + Ethers.js) ทำหน้าที่เป็น "ตู้เกม"
  - ชุดทดสอบอัตโนมัติ 60 ข้อ
  - สคริปต์ npm run demo ที่เปิดทุกอย่างได้ในคำสั่งเดียว

1.1  บล็อกเชนและ Smart Contract แบบเข้าใจง่าย
--------------------------------------------------------------------------------
บล็อกเชนเปรียบเหมือน "สมุดบัญชีกลาง" ที่ทุกคนเห็นตรงกัน
  - ทุกการเปลี่ยนแปลงต้องบันทึกเป็น "ธุรกรรม" (transaction)
  - ธุรกรรมถูกรวมเป็น "บล็อก" และบล็อกต่อกันเป็นสายด้วย hash
  - บันทึกแล้วแก้ย้อนหลังไม่ได้

Smart Contract คือ "โปรแกรมที่อาศัยอยู่บนบล็อกเชน"
  - เปรียบเหมือนตู้ขายของอัตโนมัติ: หยอดเหรียญ กดปุ่ม แล้วได้ของตามกติกาที่เขียนไว้
  - ไม่มีพนักงานคอยควบคุม และไม่มีใครแก้กติกาได้หลัง deploy
  - ในเกมนี้ กติกาทั้งหมด เช่น โอกาสสุ่ม การผสม และการหักค่าธรรมเนียม
    เขียนอยู่ใน Smart Contract หน้าเว็บมีหน้าที่แค่ "ส่งคำสั่ง" และ "แสดงผล"
    หน้าเว็บโกงกติกาไม่ได้

1.2  ERC-20: เหรียญ GEM
--------------------------------------------------------------------------------
ERC-20 คือ "มาตรฐานของเหรียญ" บน Ethereum
  - ทุกเหรียญในมาตรฐานนี้ใช้แทนกันได้ เหมือนธนบัตร 100 บาทสองใบที่มีค่าเท่ากัน
  - มีฟังก์ชันมาตรฐาน เช่น ดูยอด (balanceOf), โอน (transfer)
    และอนุญาตให้สัญญาอื่นหักเงิน (approve / transferFrom)
  - เหรียญ GEM มีทศนิยม 18 ตำแหน่งเหมือน ETH: 1 GEM = 10^18 หน่วยย่อยบนเชน
  - ไฟล์: contracts/GemToken.sol

1.3  ERC-721: ไอเทม NFT
--------------------------------------------------------------------------------
ERC-721 คือ "มาตรฐานของ NFT" (Non-Fungible Token = โทเคนที่ใช้แทนกันไม่ได้)
  - ไอเทมแต่ละชิ้นมีเลขประจำตัว tokenId ไม่ซ้ำกัน เช่น token #12
  - บนเชนตรวจได้ว่าใครเป็นเจ้าของ ได้มาเมื่อไร และเคยถูกโอนให้ใครบ้าง
  - ดาบไม้ 2 เล่มคุณสมบัติเหมือนกัน แต่เป็นคนละชิ้น เพราะ tokenId ต่างกัน
    และยังมีเลขลำดับ (serial) บอกด้วย เช่น "ดาบไม้ #27" คือดาบไม้เล่มที่ 27 ที่ถูกสร้าง
  - ไฟล์: contracts/ItemNFT.sol

1.4  On-chain Metadata: ข้อมูลไอเทมอยู่บนเชนทั้งหมด
--------------------------------------------------------------------------------
NFT ทั่วไปมักเก็บชื่อและรูปไว้บนเว็บหรือ IPFS แล้วเก็บแค่ลิงก์ไว้บนเชน
ถ้าเว็บนั้นปิด ข้อมูลก็หาย

ในเกมนี้ ฟังก์ชัน tokenURI() สร้างข้อมูลไอเทมเป็น JSON ขึ้นมา "บนเชน" ทุกครั้งที่ถูกเรียก เช่น
    {"name":"พ่อไก่ใส่เกราะหนัง #1", "attributes":[Type, Rarity, Serial, Armor, Sword]}
แล้วส่งออกมาในรูป data:application/json;base64,...

ข้อดี: ไม่พึ่งเซิร์ฟเวอร์ภายนอก ข้อมูลอยู่ตราบเท่าที่บล็อกเชนอยู่

วิธีประหยัด gas: บนเชนเก็บแค่ตัวเลข 6 ค่าต่อไอเทม แล้วค่อยแปลงเป็นชื่อตอนอ่าน
(การอ่านด้วยฟังก์ชัน view ไม่เสียค่า gas)

1.5  Local Node: บล็อกเชนจำลองในเครื่อง (Hardhat)
--------------------------------------------------------------------------------
คำสั่ง npm run demo เปิด "Hardhat Network" ซึ่งเป็นโปรแกรมที่ทำตัวเป็นโหนด Ethereum
เต็มรูปแบบอยู่ในเครื่องของเรา
  - ที่อยู่: http://127.0.0.1:8545  ·  Chain ID: 31337
  - ใช้ EVM (เครื่องประมวลผลของ Ethereum) ตัวเดียวกับเครือข่ายจริง
    Smart Contract ชุดเดียวกันนี้นำไปรันบน Sepolia หรือ Ethereum จริงได้โดยไม่ต้องแก้
  - สร้างบล็อกใหม่ทุก 3 วินาที (ตั้งไว้ใน hardhat.config.js)
    และสร้างบล็อกทันทีเมื่อมีธุรกรรมเข้ามา
  - มีบัญชีทดสอบ 20 บัญชี แต่ละบัญชีมี ETH ทดสอบ 10,000 ETH ไว้จ่ายค่า gas
      บัญชีลำดับ 0 = ผู้ deploy (owner ของสัญญา)
      บัญชีลำดับ 1, 2, 3 = ผู้เล่น 1P, 2P, 3P บนหน้าเว็บ
  - ข้อมูลอยู่ในหน่วยความจำ ปิดแล้วจะหายหมด เปิดใหม่เริ่มจากศูนย์

1.6  Auto-Sign Wallet: ทำไมไม่ต้องกดยืนยันใน MetaMask แต่ยังเป็นธุรกรรมบนบล็อกเชนจริง
--------------------------------------------------------------------------------
บนเครือข่ายจริง ทุกธุรกรรมต้อง "เซ็น" ด้วย private key ของเจ้าของบัญชี
MetaMask คือโปรแกรมที่เก็บ private key ไว้ และเด้งหน้าต่างให้เรากดยืนยันก่อนเซ็น

ในโหมด demo
  - หน้าเว็บส่งคำสั่งไปที่ Hardhat Node โดยตรง ผ่าน JsonRpcProvider ของ Ethers.js
    (โค้ดอยู่ในฟังก์ชัน connect() ของ App.jsx)
  - Hardhat Node "ถือ private key ของบัญชีทดสอบไว้เอง" และ "ปลดล็อก" บัญชีเหล่านั้นไว้แล้ว
  - เมื่อหน้าเว็บสั่งส่งธุรกรรม (eth_sendTransaction) โหนดจะเซ็นแทนเราโดยอัตโนมัติ
    จึงไม่มีหน้าต่างให้กดยืนยัน

แต่ทุกอย่างยังเป็นธุรกรรมบล็อกเชนจริง เพราะ
  1. ธุรกรรมถูกเซ็นด้วย private key จริง (เพียงแต่โหนดเป็นคนเซ็น ไม่ใช่ MetaMask)
  2. มี nonce, ค่า gas และ transaction hash เหมือนธุรกรรมบนเครือข่ายจริง
  3. ถูก EVM ประมวลผลตามกติกาใน Smart Contract ทุกบรรทัด
     ถ้าผิดกติกาจะถูกปฏิเสธ (revert) และสถานะย้อนกลับทั้งหมด
  4. ถูกบันทึกลงบล็อก มีเลขบล็อก และมี Transaction Receipt พร้อม event log
     ดูได้จริงในกล่อง BLOCKCHAIN ACTIVITY LOG

ข้อเปรียบเทียบ: เหมือนใช้ "บัญชีทดลองที่ธนาคารเปิดให้เล่น" ระบบธนาคารเป็นของจริง
แต่บัญชีเป็นบัญชีทดลองที่ธนาคารถือกุญแจไว้ให้

ข้อควรระวัง: วิธีนี้ใช้ได้เฉพาะเชนจำลองเพื่อการพัฒนาเท่านั้น
บนเครือข่ายจริง ห้ามฝาก private key ไว้กับโหนดหรือเว็บใดเด็ดขาด

1.7  ธุรกรรม, Gas, บล็อก, Receipt และ Event
--------------------------------------------------------------------------------
  - ธุรกรรม (transaction) = คำสั่งที่เปลี่ยนข้อมูลบนเชน เช่น สุ่ม ผสม ซื้อ
    ต้องจ่ายค่า gas เป็น ETH (ในเชนจำลองใช้ ETH ทดสอบ)
  - การอ่าน (view) = ถามข้อมูลโดยไม่เปลี่ยนอะไร เช่น ดูยอด GEM หรือดูไอเทม
    ฟรี ไม่ต้องสร้างธุรกรรม
  - Gas = ค่าแรงของการประมวลผล ยิ่งเขียนข้อมูลลงเชนมาก ยิ่งแพง
  - Transaction Receipt = ใบเสร็จหลังธุรกรรมถูกบันทึก บอกเลขบล็อก, hash,
    gas ที่ใช้ และ "event" ทั้งหมดที่เกิดขึ้น
  - Event = บันทึกเหตุการณ์ที่สัญญาประกาศออกมา เช่น Transfer (มีการโอน),
    Revealed (เปิดผลแล้ว), Sold (ขายแล้ว)
    หน้าเว็บอ่าน event เหล่านี้เพื่อสร้างกระเป๋าไอเทมและ Activity Log

1.8  Approve และ setApprovalForAll: การอนุญาตให้สัญญาใช้ของเรา
--------------------------------------------------------------------------------
Smart Contract ดึงเหรียญหรือไอเทมของเราเองไม่ได้ ถ้าเราไม่อนุญาตก่อน
  - approve (ERC-20): "อนุญาตให้สัญญา X หัก GEM ของฉันได้ไม่เกิน Y"
      หน้าเว็บทำให้อัตโนมัติครั้งแรกที่กดสุ่ม (อนุญาต GachaGame)
      และครั้งแรกที่กดซื้อ (อนุญาต Marketplace)
  - setApprovalForAll (ERC-721): "อนุญาตให้ร้านค้าย้าย NFT ของฉันได้"
      หน้าเว็บทำให้ครั้งแรกที่กดวางขาย
      ร้านค้าย้ายได้เฉพาะของคนที่สั่งวางขายเองเท่านั้น
  - การอนุญาตแต่ละครั้งเป็นธุรกรรมแยก จะเห็นเป็นรายการ APPROVE GEM / APPROVE NFT
    ใน Activity Log

1.9  Commit–Reveal: การสุ่มที่โกงไม่ได้
--------------------------------------------------------------------------------
ปัญหา: ถ้าสุ่มทันทีในธุรกรรมเดียว คนที่เขียน Smart Contract เป็นจะสร้างสัญญาของตัวเอง
ไว้เรียกสุ่ม แล้วสั่ง "ยกเลิก" (revert) ทุกครั้งที่ได้ของไม่ดี ทำแบบนี้ซ้ำจนได้ของดี

วิธีแก้: แบ่งเป็น 2 จังหวะ
  จังหวะที่ 1 (commit): กด PULL / FORGE / EVOLVE
      สัญญาเก็บค่าใช้จ่าย และจดเลขบล็อกปัจจุบันไว้ ตอนนี้ยังไม่มีใครรู้ผล
  จังหวะที่ 2 (reveal): รออย่างน้อย 1 บล็อก (ประมาณ 3 วินาที) แล้วกด OPEN!
      สัญญาใช้ hash ของบล็อกที่จดไว้ ผสมกับ address ผู้เล่นและตัวนับ เป็นค่าสุ่ม

ผลลัพธ์
  - ตอนจ่ายเงิน ผลยังไม่ถูกกำหนด จึงเลือกผลไม่ได้
  - ผลถูกกำหนดตายตัวด้วยบล็อกนั้นแล้ว จะยกเลิกแล้วเปิดใหม่กี่ครั้งก็ได้ผลเดิม
  - ถ้าไม่ยอมเปิดผลเกิน 256 บล็อก ระบบให้ "ผลที่แย่ที่สุด"
    (กาชาได้ Common, ผสมหรือสวมใส่นับว่าล้มเหลว)
    การตั้งใจไม่เปิดผลจึงไม่มีประโยชน์

1.10  Tokenomics: เหรียญ GEM เกิดและหายไปตอนไหน
--------------------------------------------------------------------------------
Mint (สร้างเหรียญใหม่) มีทางเดียว
  - กด INSERT COIN → GemToken.faucet() สร้าง 500 GEM ให้ผู้กด
    ค่าเริ่มต้นกดได้วันละครั้ง แต่สคริปต์ deploy ตั้ง cooldown = 0 ในโหมด demo

Burn (เผาทิ้งถาวร ทำให้เหรียญในระบบลดลง) มี 4 จังหวะ
  - สุ่มกาชา 1 ครั้ง             เผา 100 GEM   (GachaGame.pull)
  - ผสมไอเทม (FORGE)            เผา  20 GEM   (GachaGame.craft)
  - สวมใส่ (EVOLVE)              เผา  20 GEM   (GachaGame.equip)
  - ซื้อของในร้าน                เผา 5% ของราคา (Marketplace.buy)

Transfer (ย้ายเจ้าของ ไม่เพิ่มไม่ลด) มี 1 จังหวะ
  - ซื้อของในร้าน: อีก 95% ของราคาโอนจากผู้ซื้อไปให้ผู้ขาย

NFT ก็มีการสร้างและเผาเช่นกัน
  - Mint NFT: ตอนเปิดผลกาชา และตอนเปิดผลการผสม
  - Burn NFT: วัตถุดิบ 2 ชิ้นตอนผสม และอุปกรณ์ 1 ชิ้นตอนสวมใส่
  - อัปเกรดในตัว (ไม่ mint ใหม่): ตอนสวมใส่สำเร็จ tokenId เดิม แต่ข้อมูลเปลี่ยน

ภาพรวม
  faucet ──(+500)──▶ กระเป๋าผู้เล่น ──(-100/-20/-20)──▶ 🔥 เผาทิ้ง
                          │
                          └──(ซื้อของ)── 95% ──▶ ผู้ขาย
                                         5%  ──▶ 🔥 เผาทิ้ง

ในโหมด demo เหรียญเข้าระบบได้ไม่จำกัด เพราะ faucet ไม่มี cooldown
ถ้าเป็นเกมจริงต้องจำกัดการแจก ให้สมดุลกับการเผา ไม่อย่างนั้นเหรียญจะเฟ้อ

ส่วนที่ 2  เอกสารออกแบบเกม (GDD) และระบบเศรษฐกิจในเกม

2.1  วงจรการเล่นหลัก (Core Loop)
--------------------------------------------------------------------------------
  รับ GEM → สุ่มกาชา → ได้ NFT → ผสม / สวมใส่ → ได้ของหายากขึ้น
          → ขายในร้านเพื่อได้ GEM คืน → กลับไปสุ่มต่อ

2.2  ไอเทมทั้งหมดในเกม
--------------------------------------------------------------------------------
ก) ไอเทมทั่วไป 12 ชิ้น (3 ประเภท x 4 ระดับ) ได้จากตู้กาชาหรือการผสม

  ระดับ (Rarity)    ⚔️ ดาบ          🛡️ เกราะ          🐾 สัตว์เลี้ยง    พลัง (PWR)
  Common    (0)    ดาบไม้          เกราะหนัง         ลูกไก่           10
  Rare      (1)    ดาบเหล็ก        เกราะโซ่          หมาป่า           25
  Epic      (2)    ดาบเพลิง        เกราะมังกร        กริฟฟิน          60
  Legendary (3)    ดาบสุริยัน       เกราะนิรันดร์      ฟีนิกซ์           150

  * Legendary ได้จากการผสมเท่านั้น ตู้กาชาไม่ปล่อยออกมา

ข) สัตว์สวมอุปกรณ์ (Craft-Only) ได้จากโหมด EVOLVE เท่านั้น ไม่มีในตู้
   ประเภทในสัญญาคือ itemType = 3 ระดับมีตั้งแต่ Rare ถึง Mythic (4)

   ตัวอย่างชื่อ (ระบบประกอบชื่อให้อัตโนมัติจากอุปกรณ์ที่สวม):
     พ่อไก่ใส่เกราะหนัง, พ่อไก่ใส่เกราะโซ่ถือดาบเพลิง,
     พ่อไก่จักรพรรดิเกราะนิรันดร์ (เมื่อสวมเกราะนิรันดร์)
   ชื่อพิเศษตามสูตรลับ:
     หมาป่าคาบดาบเหล็ก, หมาป่าเขี้ยวอัคคี, กริฟฟินหุ้มเกราะโซ่,
     กริฟฟินเกราะเกล็ดมังกร, ฟีนิกซ์สุริยันนิรันดร์

ค) ข้อมูลที่บันทึกบนเชนต่อไอเทม 1 ชิ้น (struct Item ใน ItemNFT.sol)
     itemType   ประเภท: 0 ดาบ, 1 เกราะ, 2 สัตว์เลี้ยง, 3 สัตว์สวมอุปกรณ์
     rarity     ระดับ: 0 Common ... 4 Mythic
     serial     ลำดับที่ของไอเทมชนิดนั้น เช่น #27
     baseTier   (เฉพาะ type 3) ชนิดสัตว์ตั้งต้น: 0 ลูกไก่/พ่อไก่, 1 หมาป่า, 2 กริฟฟิน, 3 ฟีนิกซ์
     armorTier  (เฉพาะ type 3) ระดับเกราะที่สวม 0–3 หรือ 255 = ไม่ได้สวม
     swordTier  (เฉพาะ type 3) ระดับดาบที่ถือ 0–3 หรือ 255 = ไม่ได้ถือ
   ทั้ง 6 ค่ารวมกันแค่ 9 bytes อยู่ใน "storage slot" เดียว (1 slot = 32 bytes)
   การเพิ่มช่องอุปกรณ์จึงแทบไม่ทำให้ค่า gas เพิ่ม

2.3  ระบบตู้กาชา (GACHA)
--------------------------------------------------------------------------------
  ราคา: 100 GEM ต่อครั้ง (เผาทิ้งทั้งหมด)
  ขั้นตอน: กด PULL → รอประมาณ 3 วินาที → กด OPEN! → ได้ NFT 1 ชิ้น

  โอกาสได้แต่ละระดับ
     Common    70%
     Rare      25%
     Epic       5%
     Legendary  0%
  ประเภทไอเทม (ดาบ / เกราะ / สัตว์เลี้ยง) สุ่มเท่ากัน ประเภทละ 1 ใน 3

  เงื่อนไข
  - ผู้เล่น 1 คนมีคำขอค้างได้ทีละ 1 รายการ ต้องเปิดผลก่อนจึงสุ่มต่อได้
  - ต้องมี GEM อย่างน้อย 100

  จากการทดสอบสุ่ม 300 ครั้ง ได้สัดส่วนใกล้เคียงค่าที่ตั้งไว้ทุกครั้ง
  ตัวอย่างผลครั้งหนึ่ง: Common 207 / Rare 82 / Epic 11 / Legendary 0

2.4  ระบบผสมปกติ (FORGE)
--------------------------------------------------------------------------------
  ค่าใช้จ่าย: 20 GEM (เผาทิ้ง) + ไอเทม 2 ชิ้น (เผาทิ้งทันทีตอนกด FORGE)

  เงื่อนไข
  - ทั้ง 2 ชิ้นต้องเป็นของผู้เล่นเอง และต้องไม่ใช่ชิ้นเดียวกัน
  - ต้องมีระดับ (rarity) เท่ากัน
  - Legendary ผสมต่อไม่ได้ (เป็นระดับสูงสุดของไอเทมทั่วไป)
  - สัตว์สวมอุปกรณ์ (type 3) ใช้ผสมไม่ได้ ป้องกันการเผาของหายากทิ้งโดยไม่ตั้งใจ

  โอกาสสำเร็จ
     Common + Common   → Rare        80%
     Rare + Rare       → Epic        50%
     Epic + Epic       → Legendary   20%

  ผลลัพธ์
  - สำเร็จ: ได้ไอเทมระดับสูงขึ้น 1 ขั้น
  - ล้มเหลว: ได้ไอเทมระดับเดิมคืน 1 ชิ้น (จากที่ใส่ไป 2 ชิ้น)
  - ประเภทของผลลัพธ์: ถ้าวัตถุดิบเป็นประเภทเดียวกัน (เช่น ดาบ + ดาบ) จะได้ประเภทนั้น
    ถ้าต่างประเภทกัน จะสุ่ม 50/50 ระหว่างสองประเภทนั้น

2.5  ระบบวิวัฒนาการ / สวมใส่ (EVOLVE)
--------------------------------------------------------------------------------
  แนวคิด: นำ "สัตว์" 1 ตัว + "อุปกรณ์" (ดาบหรือเกราะ) 1 ชิ้น มาสวมให้กัน
  ค่าใช้จ่าย: 20 GEM (เผาทิ้ง) + อุปกรณ์ 1 ชิ้น (เผาทิ้งทันทีตอนกด EVOLVE)

  จุดเด่น: "อัปเกรดในตัวเดิม"
  - สัตว์ใช้ tokenId เดิมตลอด เช่น ลูกไก่ token #2 กลายเป็นพ่อไก่ token #2
  - สัญญาแก้ค่าใน storage slot เดิม ไม่ได้เผาตัวเก่าแล้วสร้างตัวใหม่
    จึงประหยัด gas กว่ามาก และผู้เล่นรู้สึกว่าสัตว์ตัวเดิมเติบโตขึ้น

  ระหว่างรอเปิดผล สัตว์ตัวนั้นถูก "ล็อก" (มีไอคอน 🔒) โอนหรือวางขายไม่ได้
  ป้องกันการโอนสัตว์ออกไปก่อนผลจะออก

  ตารางสูตรลับ (ตามไฟล์ gemforge_crafting_recipes.csv)
  [หมวด 2] ลูกไก่ + เกราะ → พ่อไก่ใส่เกราะ
       เกราะหนัง 90% (Rare), เกราะโซ่ 70% (Epic),
       เกราะมังกร 45% (Legendary), เกราะนิรันดร์ 25% (Mythic)
  [หมวด 3] พ่อไก่ (ต้องใส่เกราะแล้ว) + ดาบ ครั้งแรก
       ดาบไม้ 90%, ดาบเหล็ก 75%, ดาบเพลิง 50%, ดาบสุริยัน 25%
  [หมวด 4] อัปเกรดเกราะทับ (ดาบเดิมยังอยู่)
       เกราะโซ่ 75%, เกราะมังกร 45%, เกราะนิรันดร์ 20%
  [เพิ่มเติม] อัปเกรดดาบทับ (เกราะเดิมยังอยู่)
       ดาบเหล็ก 75%, ดาบเพลิง 50%, ดาบสุริยัน 25%
  [หมวด 5] สูตรลับสัตว์ระดับสูง
       หมาป่า + ดาบเหล็ก       → หมาป่าคาบดาบเหล็ก         75%
       หมาป่า + ดาบเพลิง       → หมาป่าเขี้ยวอัคคี          45%
       (หมาป่าคาบดาบเหล็ก อัปเป็นดาบเพลิงได้ 45%)
       กริฟฟิน + เกราะโซ่      → กริฟฟินหุ้มเกราะโซ่        60%
       กริฟฟิน + เกราะมังกร    → กริฟฟินเกราะเกล็ดมังกร     35%
       (กริฟฟินหุ้มเกราะโซ่ อัปเป็นเกราะมังกรได้ 35%)
       ฟีนิกซ์ + ดาบสุริยัน     → ฟีนิกซ์สุริยันนิรันดร์ (Mythic) 20%

  คู่ที่ไม่อยู่ในตาราง ระบบจะไม่ยอมให้สวม และขึ้นข้อความ "ไม่มีสูตรลับสำหรับคู่นี้"
  เช่น ลูกไก่ถือดาบก่อนใส่เกราะ หรือหมาป่าใส่เกราะ

  กติกาการอัปเกรดทับ
  - อุปกรณ์ใหม่ต้อง "ดีกว่า" ของเดิมเท่านั้น (เช็กว่า ระดับใหม่ > ระดับเดิม)
    ใส่ของเท่าเดิมหรือแย่กว่า ระบบจะปฏิเสธ
  - เปลี่ยนแค่ช่องที่อัปเกรด ช่องอื่นคงเดิม
    เช่น พ่อไก่เกราะหนังถือดาบเพลิง + เกราะโซ่ → พ่อไก่ใส่เกราะโซ่ถือดาบเพลิง

  ผลลัพธ์
  - สำเร็จ: สัตว์ได้อุปกรณ์ใหม่ ระดับและพลังเพิ่มขึ้น
  - ล้มเหลว: เสียอุปกรณ์ แต่สัตว์ยังอยู่ครบเหมือนเดิม

  สูตรคำนวณระดับ (Rarity) ของสัตว์สวมอุปกรณ์
     ระดับ = ค่าสูงสุดของ (ระดับสัตว์ตั้งต้น, ระดับเกราะ, ระดับดาบ) + 1   (สูงสุด Mythic = 4)
     ตัวอย่าง: ลูกไก่ (0) + เกราะโซ่ (1) → max(0,1) + 1 = 2 = Epic

  สูตรคำนวณค่าพลัง (PWR)
     PWR = พลังสัตว์ตั้งต้น + 1.5 x พลังเกราะ + 1.5 x พลังดาบ   (ปัดเศษลง)
     โดยพลังพื้นฐาน: ระดับ 0 = 10, ระดับ 1 = 25, ระดับ 2 = 60, ระดับ 3 = 150
     ตัวอย่าง
       พ่อไก่ใส่เกราะหนัง              10 + 1.5x10              = 25
       พ่อไก่ใส่เกราะโซ่               10 + 1.5x25 = 47.5        → 47
       พ่อไก่ใส่เกราะหนังถือดาบเพลิง   10 + 1.5x10 + 1.5x60      = 115
       พ่อไก่จักรพรรดิเกราะนิรันดร์    10 + 1.5x150              = 235
     ค่าทั้งหมดตรงกับตาราง CSV (ตรวจด้วยโปรแกรมแล้ว)
     PWR คำนวณบนหน้าเว็บ ไม่ได้เก็บบนเชน เพื่อประหยัด gas

  การเพิ่มสูตรใหม่: owner เรียก GachaGame.setRecipe(...) ได้ทันทีโดยไม่ต้อง deploy ใหม่

2.6  ระบบร้านค้า (SHOP)
--------------------------------------------------------------------------------
  การวางขาย (List)
  - เลือกไอเทมในกระเป๋า ใส่ราคาเป็น GEM แล้วกด "วางขาย"
  - NFT ถูกย้ายไป "ฝากไว้ที่ร้าน" (escrow) ระหว่างวางขาย
    เจ้าของจึงนำไปผสมหรือขายซ้ำที่อื่นไม่ได้ และรับประกันว่าผู้ซื้อจะได้ของแน่นอน
  - สัตว์ที่ถูกล็อก (รอผล EVOLVE) วางขายไม่ได้

  การยกเลิก (Cancel)
  - ยกเลิกได้เฉพาะผู้ขาย แล้วของกลับเข้ากระเป๋า

  การซื้อ (Buy) ในธุรกรรมเดียว
  - ผู้ซื้อจ่ายเต็มราคา
       95% → โอนไปให้ผู้ขาย
        5% → เผาทิ้ง (ค่าธรรมเนียม)
  - NFT ย้ายจากร้านไปที่กระเป๋าผู้ซื้อ เป็นการโอนกรรมสิทธิ์บนเชน
  - ห้ามซื้อของตัวเอง และ GEM ไม่พอจะซื้อไม่ได้
  ตัวอย่าง: ราคา 150 GEM → ผู้ขายได้ 142.5 GEM และ 7.5 GEM ถูกเผา

2.7  ความสมดุลของเศรษฐกิจ (ตัวเลขประมาณ)
--------------------------------------------------------------------------------
  เมื่อคิดรวมกรณีล้มเหลวที่ได้ของคืน 1 ชิ้น จำนวนวัตถุดิบที่ต้องใช้โดยเฉลี่ยคือ 1 + 1/โอกาสสำเร็จ
     ทำ Rare 1 ชิ้น       ใช้ Common ประมาณ 2.25 ชิ้น
     ทำ Epic 1 ชิ้น       ใช้ Rare ประมาณ 3 ชิ้น
     ทำ Legendary 1 ชิ้น  ใช้ Epic ประมาณ 6 ชิ้น
  ได้ Legendary 1 ชิ้นต้องสุ่มประมาณ 25 ครั้ง (ประมาณ 2,500 GEM) ยังไม่รวมค่าผสม
  Mythic ยากที่สุด: ต้องมีของ Legendary และผ่านโอกาสสำเร็จ 20–25%

3.2  อธิบายทีละไฟล์
--------------------------------------------------------------------------------
[ฝั่ง Smart Contract]

contracts/GemToken.sol — เหรียญ GEM (ERC-20)
  - สร้างจากแม่แบบ ERC20 + ERC20Burnable + Ownable ของ OpenZeppelin
    (ไลบรารีมาตรฐานที่ผ่านการตรวจสอบความปลอดภัยแล้ว)
  - faucet(): แจก 500 GEM ให้ผู้กด กดซ้ำได้เมื่อพ้น cooldown
  - setFaucetCooldown(): owner ตั้งเวลารอ (demo ตั้งเป็น 0)
  - burnFrom(): ให้สัญญาที่ได้รับอนุญาตเผาเหรียญของผู้เล่นได้

contracts/ItemNFT.sol — ไอเทม NFT (ERC-721)
  - เก็บข้อมูลไอเทมทุกชิ้น (struct Item) และเลข serial
  - มีชื่อไอเทมภาษาไทยทั้งหมด และสร้าง metadata JSON บนเชน (tokenURI)
  - มี "minter" ผู้เดียว (คือ GachaGame) ที่สั่ง mint / burn / อัปเกรด / ล็อกได้
  - มีระบบล็อก: ถ้าไอเทมถูกล็อก จะโอนหรือเผาไม่ได้ (ตรวจใน _update)

contracts/GachaGame.sol — สมองของเกม
  - กติกาการสุ่ม การผสม การสวมใส่ และการเปิดผลทั้งหมด
  - เก็บคำขอที่รอเปิดผลของผู้เล่นแต่ละคน (pending)

3.3  ฟังก์ชันสำคัญใน Smart Contract
--------------------------------------------------------------------------------
GemToken
  faucet()                       สร้าง 500 GEM ให้ผู้เรียก
  approve(spender, amount)       อนุญาตให้สัญญาอื่นหัก GEM ของเรา (มาตรฐาน ERC-20)
  burnFrom(account, amount)      เผา GEM ของ account (ต้องได้รับอนุญาตก่อน)

ItemNFT
  mint(to, itemType, rarity)     สร้าง NFT ใหม่ (เฉพาะ minter)
  burn(from, tokenId)            เผา NFT โดยตรวจว่า from เป็นเจ้าของจริง (เฉพาะ minter)
  setGear(tokenId, ...)          แปลงสัตว์เป็นสัตว์สวมอุปกรณ์ หรืออัปเดตอุปกรณ์ในตัวเดิม
  setLocked(tokenId, true/false) ล็อกหรือปลดล็อกไอเทม
  getItem(tokenId)               อ่านข้อมูลไอเทม (ฟรี)
  tokenURI(tokenId)              อ่าน metadata JSON บนเชน (ฟรี)

GachaGame
  pull()                         เผา 100 GEM แล้วบันทึกคำขอสุ่ม (จังหวะ commit)
  craft(a, b)                    ตรวจเงื่อนไข เผา NFT 2 ชิ้น + 20 GEM แล้วบันทึกคำขอผสม
                                 (ปุ่ม FORGE บนหน้าเว็บเรียกฟังก์ชันนี้)
  equip(creature, gear)          ตรวจสูตร ล็อกสัตว์ เผาอุปกรณ์ + 20 GEM แล้วบันทึกคำขอ
  previewEquip(player, c, g)     ตรวจล่วงหน้าว่าสวมได้ไหม ได้โอกาสเท่าไร และได้ระดับอะไร (ฟรี)
  reveal()                       เปิดผลคำขอที่ค้างอยู่ (จังหวะ reveal)
                                   กาชา → mint NFT ใหม่
                                   ผสม  → mint NFT ระดับใหม่หรือระดับเดิม
                                   สวมใส่ → ปลดล็อก แล้วอัปเกรดในตัวถ้าสำเร็จ
  revealStatus(player)           บอกสถานะ: 0 ไม่มีคำขอ, 1 รอบล็อก, 2 เปิดได้, 3 หมดเวลา
  setRecipe(...)                 owner เพิ่มหรือแก้สูตรลับ
  craftSuccessRate(rarity)       โอกาสผสมสำเร็จ 80 / 50 / 20%

Marketplace
  list(tokenId, price)           ย้าย NFT มาฝากที่ร้าน แล้วบันทึกราคา
  cancel(tokenId)                คืน NFT ให้ผู้ขาย (เฉพาะผู้ขาย)
  buy(tokenId)                   เผาค่าธรรมเนียม 5%, โอน 95% ให้ผู้ขาย, ส่ง NFT ให้ผู้ซื้อ
  getListings()                  อ่านรายการวางขายทั้งหมด (ฟรี)

3.4  เบื้องหลังเวลากดปุ่มบนหน้าเว็บ
--------------------------------------------------------------------------------
ทุกปุ่มที่เปลี่ยนข้อมูลบนเชน จะผ่านฟังก์ชัน run() ใน App.jsx ซึ่งทำงานดังนี้
  1. แสดงแถบ "กำลังส่งธุรกรรม"
  2. ส่งธุรกรรมไปที่เชนจำลอง (โหนดเซ็นให้อัตโนมัติ)
  3. รอให้ธุรกรรมถูกบันทึกลงบล็อก แล้วได้ Receipt
  4. ส่ง Receipt ไปสรุปลง BLOCKCHAIN ACTIVITY LOG
  5. ถ้าผิดพลาด แปลง error เป็นภาษาไทยแล้วแสดง
  6. โหลดยอด GEM, กระเป๋า และร้านค้าใหม่

[INSERT COIN]   → GemToken.faucet()           → ได้ 500 GEM (mint)

[PULL]          → (ครั้งแรก: GemToken.approve ให้ GachaGame)
                → GachaGame.pull()
                    ตรวจว่าไม่มีคำขอค้าง → จดเลขบล็อก → เผา 100 GEM
                → ตู้กาชาหมุน และแคปซูลตกลงช่องรับ

[OPEN!]         → GachaGame.reveal()
                    ตรวจว่าผ่านไปแล้ว 1 บล็อก → คำนวณค่าสุ่มจาก blockhash
                    → ลบคำขอ → mint หรืออัปเกรด NFT → ประกาศ event Revealed
                → หน้าต่างผลลัพธ์ เช่น "CAPSULE GET!" / "FORGED!" / "EVOLVED!"

[FORGE]         → GachaGame.craft(a, b)
                    ตรวจเจ้าของ / ระดับเท่ากัน / ไม่ใช่ Legendary / ไม่ใช่สัตว์สวมอุปกรณ์
                    → จดคำขอ → เผา NFT 2 ชิ้น → เผา 20 GEM

[EVOLVE]        → (เลือกครบ 2 ช่อง หน้าเว็บเรียก previewEquip ให้อัตโนมัติ เพื่อโชว์โอกาสสำเร็จ)
                → GachaGame.equip(creature, gear)
                    ตรวจสูตรในตาราง → จดคำขอ → ล็อกสัตว์ → เผาอุปกรณ์ → เผา 20 GEM

[วางขาย]        → (ครั้งแรก: ItemNFT.setApprovalForAll ให้ร้าน)
                → Marketplace.list(tokenId, price) → NFT ย้ายไปอยู่ที่ร้าน

[ยกเลิก]        → Marketplace.cancel(tokenId) → NFT กลับเข้ากระเป๋า

[ซื้อ]          → (ครั้งแรก: GemToken.approve ให้ร้าน)
                → Marketplace.buy(tokenId)
                    ลบรายการ → เผา 5% → โอน 95% ให้ผู้ขาย → ส่ง NFT ให้ผู้ซื้อ

[COPY]          → คัดลอก Transaction Hash เต็มจาก Activity Log (ไม่ใช่ธุรกรรม)

3.5  หน้าเว็บรู้ได้อย่างไรว่าเรามีไอเทมอะไรบ้าง
--------------------------------------------------------------------------------
มาตรฐาน ERC-721 ไม่มีฟังก์ชัน "ขอรายการไอเทมทั้งหมดของฉัน"
หน้าเว็บจึงทำแบบนี้
  1. ค้นหา event Transfer ทั้งหมดที่ "ส่งมาหาเรา" ตั้งแต่บล็อกที่ deploy
  2. ตรวจแต่ละชิ้นว่ายังเป็นของเราอยู่ไหม (ownerOf)
     ชิ้นที่ถูกเผาหรือขายไปแล้วจะถูกตัดออก
  3. อ่านข้อมูลด้วย getItem() แล้วแสดงในกระเป๋า (BAG)
วิธีนี้เป็นตัวอย่างการใช้ "event" แทนการเก็บรายการบนเชน ซึ่งประหยัด gas กว่า

4.3  สคริปต์การสาธิตทีละขั้น (ประมาณ 10–12 นาที)
--------------------------------------------------------------------------------
ขั้นที่ 1  แนะนำหน้าจอ (1 นาที)
  - ป้ายไฟด้านบน: ช่อง PLAYER (1P) และ CREDIT (ยอด GEM ตอนนี้เป็น 0)
  - จอหลักมี 4 โหมด: GACHA / FORGE / EVOLVE / SHOP
  - ด้านขวาคือกระเป๋า (BAG) ด้านล่างคือ BLOCKCHAIN ACTIVITY LOG
  - พูดว่า: "ทุกปุ่มคือธุรกรรมจริงบนบล็อกเชนจำลอง ไม่ต้องกด MetaMask
    เพราะโหนดเซ็นแทนบัญชีทดสอบให้" (อธิบายตามหัวข้อ 1.6)

ขั้นที่ 2  รับเหรียญ (Mint ERC-20)
  - กด INSERT COIN ที่แผงควบคุมด้านล่าง 2–3 ครั้ง
  - ชี้ให้ดู: CREDIT เพิ่มขึ้นครั้งละ 500 และ Activity Log ขึ้นว่า
      [Block #..] INSERT COIN | Tx: 0x.... | +500 GEM

ขั้นที่ 3  สุ่มกาชา (Burn GEM + Mint NFT + Commit–Reveal)
  - เลือกโหมด GACHA แล้วกด PULL ✦ 100 GEM
  - ครั้งแรกจะมี 2 ธุรกรรม คือ APPROVE GEM แล้ว GACHA PULL
  - ชี้ให้ดู: ตู้หมุน แคปซูลตกลงช่อง และแถบ "PLEASE WAIT"
    อธิบายว่ารอ 1 บล็อกเพื่อกันการโกงสุ่ม (commit–reveal)
  - เมื่อแถบเป็น "READY!" กด OPEN!
  - ชี้ให้ดู: หน้าต่าง "CAPSULE GET!" แสดงไอเทม เลข serial และค่าพลัง
    Activity Log มีทั้ง "-100 GEM (เผาทิ้ง)" และ "MINT NFT #.."
  - สุ่มต่ออีกประมาณ 5–8 ครั้ง เพื่อให้มีของพอใช้ในขั้นต่อไป
    ควรได้ลูกไก่ เกราะ และไอเทม Common อย่างน้อย 2 ชิ้นที่ประเภทเดียวกัน

ขั้นที่ 4  ผสมไอเทม (Burn 2 NFT → Mint 1 NFT)
  - เลือกโหมด FORGE แล้วแตะไอเทม Common 2 ชิ้นในกระเป๋า
  - ชี้ให้ดู: ข้อความ "โอกาสสำเร็จ 80% → Rare"
  - (ทางเลือก) ลองแตะ 2 ชิ้นที่ระดับต่างกัน ปุ่ม FORGE จะกดไม่ได้
    และขึ้นข้อความเตือน = กติกาถูกบังคับ
  - กด FORGE แล้วกด OPEN!
  - ชี้ให้ดู: Activity Log ขึ้น "BURN NFT #a · BURN NFT #b"
    แล้วตามด้วย "MINT NFT #ใหม่" = Burn & Mint จริงบนเชน

ขั้นที่ 5  วิวัฒนาการ (Craft-Only NFT + อัปเกรดในตัว)
  - เลือกโหมด EVOLVE แล้วแตะลูกไก่ 1 ตัว และเกราะหนัง 1 ชิ้น
  - ชี้ให้ดู: ช่องผลลัพธ์แสดงการ์ด "พ่อไก่ใส่เกราะหนัง" ล่วงหน้า
    พร้อมโอกาส 90% (อ่านจากเชนด้วย previewEquip)
  - (ทางเลือก) ลองแตะลูกไก่ + ดาบ จะขึ้น "ไม่มีสูตรลับสำหรับคู่นี้"
  - จดเลข token ของลูกไก่ไว้ แล้วกด EVOLVE
    ชี้ไอคอน 🔒 ที่ลูกไก่ (ล็อกระหว่างรอผล)
  - กด OPEN! → "EVOLVED!"
    ชี้ให้ดูว่าเลข token ยังเป็นเลขเดิม = อัปเกรดในตัว ไม่ได้สร้างใหม่
  - (ถ้ามีดาบไม้) สวมดาบให้พ่อไก่ต่อ → "พ่อไก่ใส่เกราะหนังถือดาบไม้" PWR 40
  - เปิดสมุดสูตรลับ (RECIPE BOOK) ด้านล่างให้ดูสูตรทั้งหมด

ขั้นที่ 6  ร้านค้า (โอนกรรมสิทธิ์ NFT + เผาค่าธรรมเนียม 5%)
  - เลือกโหมด SHOP ในฐานะ 1P แตะไอเทม 1 ชิ้น ใส่ราคา 150 แล้วกด "วางขาย"
  - ชี้ให้ดู: ไอเทมหายจากกระเป๋าไปอยู่ใน "ON SALE" (ฝากไว้ที่ร้าน)
  - เปลี่ยน PLAYER เป็น 2P
    ชี้ให้ดูว่ากระเป๋าของ 2P ว่าง = แต่ละบัญชีมีของแยกกันจริง
  - 2P กด INSERT COIN แล้วกด "ซื้อ" ที่ไอเทมของ 1P
  - ชี้ให้ดูบรรทัดใน Activity Log

5.1  การป้องกันที่ใส่ไว้ (เชื่อมกับเนื้อหาสัปดาห์ที่ 9)
--------------------------------------------------------------------------------
  1. Checks-Effects-Interactions (CEI)
     ตรวจเงื่อนไขก่อน → บันทึกข้อมูลของตัวเองก่อน → ติดต่อสัญญาอื่นหรือโอนของทีหลังสุด
     ตัวอย่าง: reveal() ลบคำขอก่อน แล้วค่อย mint NFT (การ mint มีการเรียกกลับไปหาผู้รับ)

  2. nonReentrant (ป้องกัน re-entrancy)
     ทุกฟังก์ชันที่ผู้เล่นเรียกในเกมและร้านค้า ป้องกันการเรียกซ้ำกลางทาง
     แบบที่เกิดในเหตุการณ์ The DAO
     ได้ทดลองถอดตัวป้องกันออก แล้วชุดทดสอบตรวจพบการโจมตีทันที (พิสูจน์ว่า test ได้ผล)

  3. Access Control (ควบคุมสิทธิ์)
     - มีแค่ "minter" (ตั้งเป็น GachaGame) ที่ mint / burn / อัปเกรด / ล็อก NFT ได้
       owner ไม่มีปุ่มสร้าง NFT ตรง ๆ ต้องผ่านกติกาของ GachaGame เท่านั้น
     - burn() ตรวจซ้ำว่าเผาของเจ้าของที่ถูกต้อง
     - การตั้งค่าและการเพิ่มสูตรทำได้เฉพาะ owner
     - ข้อควรรู้: owner ยังมีสิทธิ์เปลี่ยน minter ได้ (ชุดทดสอบใช้สิทธิ์นี้จัดฉากไอเทม)
       ถ้าเป็นระบบจริง ควรมอบสิทธิ์ owner ให้ multisig หรือสละสิทธิ์ (renounceOwnership)
       หลังตั้งค่าเสร็จ เพื่อไม่ให้คนคนเดียวมีอำนาจมากเกินไป

  4. Commit–Reveal (ป้องกันการเลือกผลสุ่ม) ตามหัวข้อ 1.9

  5. ล็อกไอเทมระหว่างรอผล (ป้องกันสถานะครึ่ง ๆ กลาง ๆ)
     สัตว์ที่กำลังสวมใส่ โอนหรือวางขายไม่ได้จนกว่าจะเปิดผล

  6. Solidity 0.8 ตรวจตัวเลขล้น (overflow) ให้อัตโนมัติ

ส่วนที่ 7  คำถามที่อาจถูกถามตอนนำเสนอ (พร้อมคำตอบ)

ถาม: ไม่ได้กด MetaMask เลย แบบนี้ยังเป็นบล็อกเชนจริงไหม
ตอบ: เป็นธุรกรรมจริงบน EVM ครับ มีลายเซ็น, nonce, gas, เลขบล็อก และ Transaction Hash
     ครบทุกอย่าง ต่างกันแค่ผู้เซ็นคือโหนดที่ถือกุญแจของบัญชีทดสอบ ไม่ใช่ MetaMask
     (รายละเอียดหัวข้อ 1.6)

ถาม: ไอเทม Common สองชิ้นเหมือนกันหรือเปล่า
ตอบ: คุณสมบัติในเกมเหมือนกัน แต่ tokenId และ serial ต่างกัน
     เป็น NFT คนละชิ้น มีเจ้าของและประวัติแยกกัน

ถาม: ทำไมสุ่มแล้วต้องรอ ไม่ให้ผลทันที
ตอบ: เพื่อป้องกันผู้เล่นที่เขียนสัญญาเองมาสุ่มแล้วยกเลิกเมื่อได้ของไม่ดี (commit–reveal)
     มี test พิสูจน์ว่าการโจมตีนี้ทำไม่ได้

ถาม: ทำไมสวมเกราะแล้วไม่สร้าง NFT ใหม่
ตอบ: แก้ข้อมูลในตัวเดิมถูกกว่าการเผาแล้วสร้างใหม่มาก เพราะเขียน storage slot เดิมแค่ครั้งเดียว
     และผู้เล่นได้สัตว์ตัวเดิมที่เติบโตขึ้น

ถาม: ใครเป็นคนกำหนดโอกาสสุ่ม แก้ได้ไหม
ตอบ: โอกาสของกาชาและการผสมเขียนตายตัวในสัญญา ไม่มีใครแก้ได้
     สูตรลับของการสวมใส่ owner เพิ่มหรือแก้ได้ผ่าน setRecipe
     ทุกการแก้มี event RecipeSet บันทึกไว้ให้ตรวจสอบย้อนหลังได้

ถาม: ร้านค้าโกงผู้ซื้อได้ไหม เช่น รับเงินแล้วไม่ส่งของ
ตอบ: ไม่ได้ เพราะของถูกฝากไว้ที่สัญญาตั้งแต่ตอนวางขาย
     และการจ่ายเงินกับการส่งของเกิดในธุรกรรมเดียว ถ้าขั้นใดผิดพลาด ทั้งหมดถูกยกเลิก

ถาม: เหรียญที่เผาไปหายไปไหน
ตอบ: ถูกลบออกจากระบบถาวร จำนวนเหรียญทั้งหมด (totalSupply) ลดลง
     ใน receipt จะเห็นเป็นการโอนไปที่ address 0

ถาม: ถ้าเครื่องปิด ข้อมูลหายไหม
ตอบ: เชนจำลองเก็บในหน่วยความจำ ปิดแล้วหาย ซึ่งเหมาะกับการสาธิต
     ถ้า deploy บนเครือข่ายจริง ข้อมูลจะอยู่ถาวร

9.1  ปัญหาของเกมกาชาทั่วไป และความเชื่อใจที่ระบบเราตัดออก
--------------------------------------------------------------------------------
  เกมกาชาทั่วไป ผู้เล่นต้อง "เชื่อใจ" บริษัทใน 4 เรื่อง

  ปัญหา 1: ประกาศอัตราดรอป แต่ผู้เล่นตรวจไม่ได้
     ต้องเชื่อว่า: เซิร์ฟเวอร์ไม่แอบแก้อัตรา
     GemForge:   อัตราเขียนไว้ในสัญญา ใครก็เปิดอ่านโค้ดได้ และแก้ไม่ได้

  ปัญหา 2: ไอเทมเป็นแค่แถวในฐานข้อมูลของบริษัท
     ต้องเชื่อว่า: บริษัทไม่ลบของ ไม่ปิดเกม ไม่แบนบัญชี
     GemForge:   ไอเทมเป็น NFT ผูกกับ address ของผู้เล่นเอง

  ปัญหา 3: ซื้อขายไอเทมระหว่างผู้เล่น ต้องผ่านคนกลาง
     ต้องเชื่อว่า: อีกฝ่ายจ่ายเงินหรือส่งของจริง
     GemForge:   ร้านค้าแบบ escrow แลกเงินกับของในธุรกรรมเดียว
                 ถ้าขั้นไหนพลาด ทั้งธุรกรรมถูกยกเลิก ไม่มีใครเสียของฟรี

  ปัญหา 4: บริษัทเสกของหายากเพิ่มได้เงียบ ๆ
     ต้องเชื่อว่า: บริษัทไม่ทำให้ของเฟ้อ
     GemForge:   การสร้าง (mint) และเผา (burn) ทุกครั้งมี event ตรวจย้อนหลังได้

9.2  ทำไมไม่ใช้ฐานข้อมูลธรรมดา
--------------------------------------------------------------------------------
  ฐานข้อมูลเร็วกว่าและถูกกว่าจริง แต่ "ผู้ดูแลแก้ข้อมูลได้เสมอ"
  สิ่งที่เราต้องการคือ ผลลัพธ์ที่ผู้เล่นตรวจสอบได้เอง โดยไม่ต้องเชื่อใคร
  จึงใช้บล็อกเชนเฉพาะส่วนที่ต้องการความเชื่อใจ ส่วนอื่นยังอยู่นอกเชน (ดูส่วนที่ 10)

  ยอมรับตรง ๆ: ในระบบเรา owner ยังตั้งสูตรและเปลี่ยน minter ได้
  ถ้าเป็นระบบจริง ควรมอบสิทธิ์ owner ให้ multisig หรือสละสิทธิ์ (renounceOwnership)

ส่วนที่ 10  การแบ่งข้อมูล On-chain และ Off-chain
================================================================================

  หลักการแบ่ง: ถามว่า "ถ้าข้อมูลนี้ถูกคนกลางแก้ ผู้เล่นเสียหายไหม"
  ถ้าเสียหาย → อยู่บนเชน   ถ้าไม่เสียหาย (แค่การแสดงผล) → อยู่นอกเชน

  อยู่บนเชน (On-chain)                      อยู่นอกเชน (Off-chain)
  ----------------------------------------  ----------------------------------------
  ยอด GEM และเจ้าของ NFT                    หน้าเว็บ ธีมตู้เกม อีโมจิ
  ข้อมูลไอเทม 9 ไบต์ต่อชิ้น (1 slot)         Activity Log (สร้างใหม่จาก receipt)
  อัตรากาชา อัตราผสม สูตร EVOLVE            ชื่อผู้เล่น 1P / 2P / 3P
  คำขอที่รอเปิดผล (commit)                  สำเนาตารางอัตรา ไว้แสดงผลเท่านั้น
  รายการขายในร้าน (escrow)                  private key (อยู่ใน wallet / โหนด)
  event ของทุกการกระทำ

  การระวังไม่เก็บบนเชนเกินจำเป็น
  - ชื่อสัตว์ 96 แบบ ไม่ได้เก็บเป็นข้อความ แต่สร้างจาก tier ตอนอ่าน (view ไม่เสีย gas)
  - ประวัติการเล่นดูจาก event ไม่ต้องเขียนลง storage
  - metadata คำนวณใน tokenURI ไม่ต้องพึ่ง IPFS หรือเซิร์ฟเวอร์

ส่วนที่ 11  วิเคราะห์ช่องโหว่ของสัญญาเรา (ผูกกับโค้ดจริง)
================================================================================

  รูปแบบ: ช่องโหว่ → ถ้าไม่ป้องกันจะโดนอย่างไร → วิธีป้องกัน → ตำแหน่งในโค้ด

  1. Re-entrancy (เรียกซ้ำกลางทาง)
     โดนอย่างไร: _safeMint จะเรียก onERC721Received ไปที่ผู้รับ
                 ถ้าผู้รับเป็นสัญญาผู้โจมตี มันจะเรียก pull() ซ้ำระหว่างที่ reveal ยังไม่เสร็จ
     ป้องกัน:    nonReentrant ทุกฟังก์ชันที่เปลี่ยนสถานะ + CEI (ลบ pending ก่อน mint)
     ในโค้ด:     GachaGame.sol บรรทัด 224 และ 252
     test:       สัญญา ReentrantPlayer ใน contracts/test/AttackerContracts.sol

  2. Bad Randomness (โกงการสุ่ม)
     โดนอย่างไร: สัญญาผู้โจมตีสุ่มและเปิดผลในธุรกรรมเดียว
                 ถ้าได้ของไม่ดีก็สั่ง revert แล้วลองใหม่ จนกว่าจะได้ของดี
     ป้องกัน:    Commit–Reveal ต้องเปิดผลในบล็อกถัดไป (error TooEarly)
                 เกิน 256 บล็อก ได้ผลแย่ที่สุด จึงตั้งใจไม่เปิดก็ไม่ได้ประโยชน์
     ในโค้ด:     GachaGame.sol บรรทัด 228, 230 และ 351
     test:       สัญญา SameTxRerollAttacker

  3. Access Control (ควบคุมสิทธิ์)
     โดนอย่างไร: ใครก็เรียก mint() สร้าง Legendary ให้ตัวเองได้
     ป้องกัน:    onlyMinter (มีแค่ GachaGame) และ onlyOwner สำหรับการตั้งค่า
     ในโค้ด:     ItemNFT.sol บรรทัด 66 และ 85, GachaGame.sol บรรทัด 294

  4. Double-use ระหว่าง EVOLVE
     โดนอย่างไร: ส่งคำขอ EVOLVE แล้วรีบขายหรือโอนสัตว์ตัวนั้นก่อนเปิดผล
     ป้องกัน:    ล็อก NFT ระหว่างรอผล ถ้าโอน _update จะ revert ด้วย ItemLocked
     ในโค้ด:     GachaGame.sol บรรทัด 178, ItemNFT.sol บรรทัด 145

  5. Trade Fraud (โกงในการซื้อขาย)
     โดนอย่างไร: ผู้ขายรับเงินแล้วไม่ส่งของ
     ป้องกัน:    escrow — NFT ฝากไว้ที่สัญญาตั้งแต่ลงขาย
                 ตอนซื้อ จ่ายเงิน เผาค่าธรรมเนียม และส่งของ เกิดในธุรกรรมเดียว
     ในโค้ด:     Marketplace.sol บรรทัด 53 และ 69–83

  การจัดการข้อผิดพลาดของธุรกรรม: ทุกเงื่อนไขใช้ custom error
  หน้าเว็บ (frontend/src/errors.js) แปลเป็นข้อความภาษาไทยให้ผู้เล่นอ่านเข้าใจ

ส่วนที่ 12  เปรียบเทียบ Layer 1 กับ Layer 2
================================================================================

  หัวข้อ              L1 (Ethereum)                L2 Rollup (Arbitrum, Optimism, zkSync, Base)
  ------------------  ---------------------------  ---------------------------------------------
  ประมวลผลที่ไหน      บน Ethereum โดยตรง            นอก L1 แล้วส่งข้อมูลสรุปกลับไปเก็บบน L1
  ความปลอดภัย         ของ Ethereum เอง              อิง L1 (fraud proof หรือ ZK proof)
  ค่า gas             สูง ผันผวนตามความแออัด         ถูกกว่าหลายสิบเท่าขึ้นไป
  เวลายืนยัน          บล็อกละประมาณ 12 วินาที        ไม่ถึงวินาที ถึงประมาณ 2 วินาที
  ถอนกลับ L1          -                            Optimistic รอประมาณ 7 วัน, ZK เร็วกว่า

  gas ที่วัดจริงจากสัญญาเรา (บน Hardhat)
    faucet 42,369 · pull 66,127 · reveal (กาชา) 123,070
    craft 110,156 · reveal (ผสม) 122,434
    equip 131,412 · reveal (สวมใส่) 78,470
    list 160,486 · buy 97,131

  กาชา 1 ครั้ง = 2 ธุรกรรม รวมประมาณ 189,000 gas
  ถ้าราคา gas 10 gwei (ตัวอย่างสมมติ) จะเสียประมาณ 0.0019 ETH ต่อครั้ง

  สรุป: เกมมีธุรกรรมเล็ก ๆ บ่อย ๆ จึงเหมาะกับ L2
  สัญญาเราเป็นโค้ด EVM ธรรมดา จึง deploy บน L2 ที่รองรับ EVM ได้โดยไม่ต้องแก้

ส่วนที่ 13  บทเรียนที่ได้
================================================================================

  1. การสุ่มบนเชนยากกว่าที่คิด — ทุกอย่างเปิดเผยและ revert ได้ จึงต้องใช้ commit–reveal
  2. ทุกไบต์มีราคา — อัดข้อมูลไอเทมเหลือ 1 slot, ไม่เก็บข้อความ, ใช้ event แทนประวัติ
  3. test ต้องโจมตีจริง — เขียนสัญญาผู้โจมตีมาทดสอบ จึงมั่นใจว่ากลไกป้องกันใช้ได้
  4. เศรษฐกิจต้องมีทางออก — มีเหรียญเข้า (faucet) ก็ต้องมีทางเผา (burn) ไม่งั้นเหรียญเฟ้อ
  5. UX สำคัญเท่าสัญญา — ต้องแปล error และแสดง receipt ให้ผู้เล่นเข้าใจว่าเกิดอะไรบนเชน
  6. บล็อกเชนไม่ใช่คำตอบของทุกอย่าง — แพงและช้ากว่าฐานข้อมูล ใช้เฉพาะส่วนที่ต้องการความเชื่อใจ
